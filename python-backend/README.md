# Vehicle Dashboard — Python Backend

A small FastAPI service that produces **simulated** vehicle data for the Android
dashboard client, and receives, validates and logs the values the client is
currently displaying.

There is no real vehicle signal, no external service and no database. All data
originates from one deterministic simulator inside this project.

---

## Architecture

The service is deliberately four small modules. Each has one job, so each can be
explained and tested on its own.

| File | Responsibility |
|---|---|
| `app/main.py` | The FastAPI app and the three endpoints. Thin by design: validate → simulate → log → respond. |
| `app/simulator.py` | The single source of simulated vehicle data. |
| `app/models.py` | Pydantic models: the API contract and all value validation. |
| `app/logging_config.py` | Configures the timestamped file logger. |
| `conftest.py` | Shared pytest fixtures (in-process test client, valid payload). |
| `tests/test_api.py` | The automated tests. |

### The simulator

`DashboardSimulator.snapshot(now)` turns a timestamp into a complete dashboard
state. Everything except the media player is a pure function of that timestamp,
which means the values change smoothly while the server runs *and* the tests are
fully deterministic — no `sleep()`, no mocking of the clock.

The simulation repeats a **120-second trip** so that a reviewer sees every
driving status quickly instead of waiting for a realistic trip length:

| Seconds in cycle | Driving status | Behaviour |
|---|---|---|
| 0 – 15 | `Parked` | Speed 0, battery 82 %, full distance to destination |
| 15 – 95 | `Driving` | Speed follows two summed sine waves; battery drains 82 % → 61 %; distance counts down |
| 95 – 120 | `Charging` | Speed 0, arrived at the destination, battery recharges 61 % → 82 % |

Outside temperature is a slow 10-minute sine wave between roughly 11 °C and
24 °C. The media player is the one piece of mutable state, because a paused
track must not keep advancing — its position cannot be derived from the clock.

### Why both a GET and a POST

The assignment's wording is ambiguous. It says the backend *"just provides
simulated data"*, and also asks for an endpoint that *"receives the processed
data results from the Android client and provides status and values"*.

Those are two different directions of data flow, so they are implemented as two
endpoints:

* **`GET /api/dashboard`** keeps the simulation in exactly one place. The
  Android app displays it and runs no simulation of its own.
* **`POST /api/dashboard/sync`** fulfils the receive-and-log requirement. It
  takes the values the client is currently displaying plus the driver's media
  action, validates them, writes one timestamped line to the log file, and
  answers with a status and the accepted values.

A useful side effect: the POST also carries the play/pause intent, so the button
in the app changes the simulation that the app is polling. One source of truth.

## Endpoints

| Method | Path | Purpose | Success |
|---|---|---|---|
| `GET` | `/health` | Liveness check; the app uses it to distinguish "down" from "slow" | `200` |
| `GET` | `/api/dashboard` | Current simulated vehicle state | `200` |
| `POST` | `/api/dashboard/sync` | Receive displayed values + media action, log them, acknowledge | `200`, or `422` if a value is out of range |
| `GET` | `/docs` | Interactive Swagger UI, generated by FastAPI | `200` |

### Validation

Every range from the assignment is enforced by Pydantic, not by comments:

| Field | Range |
|---|---|
| speed | 0 – 250 km/h |
| battery | 0 – 100 % |
| outside temperature | −20 – +50 °C |
| driving status | `Parked` \| `Driving` \| `Charging` |
| media progress | 0 – 100 % |

An out-of-range value is rejected with `422` **before** the handler runs, so an
impossible value can never reach the log file.

## Running

**For browser / Swagger testing only** — binds to localhost:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

Then open <http://127.0.0.1:8000/docs>.

**For the Android emulator** — must bind all interfaces:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

The emulator cannot reach a server bound only to `127.0.0.1`, because inside the
emulator `127.0.0.1` means the emulated device itself. See the Android README
for the `10.0.2.2` explanation.

## Example request and response

### `GET /api/dashboard`

```json
{
  "timestamp": "2026-07-30T18:50:37.412Z",
  "speed_kmh": 153,
  "battery_percent": 76,
  "outside_temperature_c": 20.0,
  "driving_status": "Driving",
  "media": {
    "is_playing": true,
    "track_name": "Night Drive",
    "progress_percent": 83
  },
  "navigation": {
    "destination": "Riverside Charging Hub",
    "remaining_minutes": 40,
    "distance_km": 30.2
  }
}
```

### `POST /api/dashboard/sync`

Request body:

```json
{
  "displayed_speed_kmh": 153,
  "displayed_battery_percent": 76,
  "displayed_temperature_c": 20.0,
  "displayed_driving_status": "Driving",
  "media": { "is_playing": true, "track_name": "Night Drive", "progress_percent": 83 },
  "navigation": { "destination": "Riverside Charging Hub", "remaining_minutes": 40, "distance_km": 30.2 },
  "media_action": "toggle"
}
```

Response:

```json
{
  "status": "accepted",
  "received_at": "2026-07-30T18:50:59.616Z",
  "logged_to": "...\\python-backend\\logs\\dashboard.log",
  "values": { "...": "the validated values, echoed back" }
}
```

A rejected request returns `422` with the offending field named:

```json
{"detail":[{"type":"less_than_equal","loc":["body","displayed_speed_kmh"],
 "msg":"Input should be less than or equal to 250","input":300}]}
```

## Logging

* **Location:** `python-backend/logs/dashboard.log`
* **Written when:** the app calls `POST /api/dashboard/sync`. In the current
  Android client that happens **when the driver presses play/pause** — there is
  no automatic periodic synchronisation. The log therefore grows on interaction,
  not continuously.
* **Format:** one line per event, timestamp first, payload as JSON so the line
  stays both human-readable and machine-parsable.

```
2026-07-30T18:51:16.125Z | INFO | RECEIVED | {"displayed_speed_kmh":0, ... ,"media_action":"pause"}
```

Timestamps are UTC with milliseconds, matching the UTC timestamps in the API
responses, so a log line can be lined up with a payload. A
`TimedRotatingFileHandler` starts a new file at midnight UTC. Startup and
shutdown markers (`BACKEND STARTED` / `BACKEND STOPPED`) delimit each run.

## Tests

```powershell
cd "D:\Development Task\VehicleDashboardAssignment\python-backend"
.\.venv\Scripts\python.exe -m pytest -q
```

**Verified result: `16 passed`**, with one non-critical warning from FastAPI's
own test client (a Starlette deprecation notice about `httpx` vs `httpx2`) that
comes from the library, not from this project.

The tests cover four groups:

1. **Endpoint responses** — status codes and the shape of each payload.
2. **Simulated ranges** — two full 120-second cycles are walked second by
   second and every value is checked against the assignment's limits. This runs
   in milliseconds precisely because the simulator takes a timestamp.
3. **POST validation** — six out-of-range values each produce `422`.
4. **Timestamped logging** — a real POST is made, the log file is read back, the
   timestamp is matched with a regex and the JSON is parsed out of the line.

## Known limitations

* The 120-second trip cycle is tuned for a demo, not for realism.
* No persistence: state lives in memory and resets when the server restarts.
* No authentication and no TLS. Plain HTTP on a local development machine only.
* No log retention policy — files rotate daily but are never deleted.
* One shared simulator instance means all clients see the same vehicle. That is
  correct for "one car", but it is not multi-tenant.
* The API sends remaining distance but not the total trip length, so the client
  has to infer route progress. A `total_distance_km` field would remove that.
* Concurrency and midnight log rotation are not covered by the tests.
